# 競輪版 買い目ジェネレーター（器）

競馬の KB1013（複数予想ソースの印＋数値指標を入力に、固定メニューの買い目を
自動生成して回収率を検証する仕組み）を競輪に移植するための**フレームワーク**。
ルールの中身ではなく「器」であり、同梱ルールはどれも実演用で、
「勝てる法則」として検証済みのものは1つも無い。

設計思想は1つだけ：**ルールは JSON で差し替え可能にし、生成→精算→
前半/後半に分けた集計までを自動化する**。法則が本物かどうかは、
この器の前向き運用と分割集計で判定する（勝者の呪い対策）。

## 構成

| ファイル | 役割 |
|---|---|
| `inputs.py` | 入力の統一層。全ソースを「1レース=1 dict」にまとめる |
| `rules.py` | ルール定義（セレクタ／条件／買い目）の解決エンジン |
| `engine.py` | 生成＋精算（払戻金JSON照合、100円/点）＋ルール別集計（前半/後半つき） |
| `gen.py` | CLI（demo / forward / settle） |
| `rules_sample.json` | サンプルルール7個 |
| `data/` | Supabase ダンプのキャッシュ（下表） |
| `forward/` | 前向き生成の保存先（`YYYY-MM-DD.json`） |
| `report_demo.json` | demo の詳細出力（全買い目の精算結果つき） |

### 記者印の扱い（既知の制約）
Kドリームス記者の印は DB 化されていない。器は「あれば取り込む」
インターフェースとし、現在は次の2つから読む：
- `~/workspace/majima/watch/*.json`（真島・八角ウォッチで保存した 31レース）
- `~/workspace/majima/today_parsed_*.json`（parse_lib.py 形式の全レース解析
  キャッシュ、2026-11-16〜18 の3日分・記者名が取れたレースのみ）

**全レース分の記者印を毎日自動で取り込む仕組みは未実装**（今回の範囲外）。
前向き運用で記者系ルールを使い続けるなら、この収集の自動化が次の課題。

## ルール JSON の書き方

```json
{"id": "my_rule", "name": "表示名", "description": "意図",
 "when": [条件...], "bet": {...}, "stake": 100}
```

### セレクタ（選手=車番の集合を指す）
| 書き方 | 意味 |
|---|---|
| `journalist.◎` `journalist.○` `journalist.▲` `journalist.△` `journalist.×` `journalist.注` | 記者の印 |
| `kc_ai.1`〜`kc_ai.3` / `kc_ai.top3` | KEIRINCRAFT AI（朝版）の順位/top3 |
| `kc_stats.1` など / `kc_ai_narabi.1` / `kc_stats_narabi.1` | 統計版・並び後版 |
| `pro:<予想家名>.axis` | その予想家のフォーメーション1列目 |
| `pro_consensus.axis` | PRO予想家の1列目に最も多く入った選手 |
| `score.1` `score.2` `score.3` | 競走得点の順位 |

### 条件（`when`、全て満たせば発動）
- `{"type":"same_rider","a":ref,"b":ref}` 共通の選手がいる
- `{"type":"in_set","a":ref,"b":ref}` a が b に含まれる
- `{"type":"journalist_is","name":"真島秀昭"}` 担当記者（部分一致）
- `{"type":"score_rank_of","ref":ref,"rank":1}` ref の選手の得点順位
- `{"type":"score_gap","min":3.0}` 得点1位と2位の差
- `{"type":"pro_consensus_count","min":2}` 軸一致の予想家数
- `{"type":"overlap_count","a":ref,"b":ref,"min":2}` 共通選手数

### 買い目（`bet`）
- `{"type":"2車単","from":ref,"to":ref}`
- `{"type":"ワイド","a":ref,"b":ref}`
- `{"type":"3連複","box":[ref,ref,ref]}`（3選手に解決されれば1点、多い場合は全組合せ）
- `{"type":"3連単","order":[ref,ref,ref]}`
- `{"type":"2車単フォーメーション","axis":ref,"partners":ref}`

## CLI の使い方

```bash
cd keirin_generator   # このフォルダ内で実行（データは data/ に取得される）
python3 gen.py demo                          # 過去データで実演+精算+集計表
python3 gen.py forward --date 2026-11-18     # 当日分を生成し forward/ に保存
python3 gen.py settle  --date 2026-11-18     # 結果が出たら精算 (同じファイルに書き戻し)
python3 gen.py forward --date 2026-11-19 --fetch   # Supabase から再取得してから生成
```
`--fetch` は race_memos / external_predictions / race_results を更新する。
player_stats（62MB）も更新するときは `--fetch-all`。

読み方の注意：
- **検証そのものの正しさ**：真島ルールの集計（21R・3的中・40.5%、前半60.7%/
  後半0.0%）は、記者ウォッチの手作業精算と完全一致した。器の精算は信用できる。
- **判定不可のもの**：記者系・KC系ルールは対象期間が 2026-11-09〜17 の
  最大9日間しかない。前半/後半を分けても数日ずつの比較にすぎず、
  「実演用・判定不可」。PRO系も構造化データが 10-25 以降のみで期間は短い。
- 全ルールが回収率100%未満で、過去のマイニング結果と整合する。
  器は「法則が無いこと」を示すためにもある。

前向きループの動作確認：2026-11-17 分を forward→settle すると 302/302点が
精算まで完了。2026-11-18 分は 286点を生成済み（結果はDB未投入のため精算待ち）。

## 既知の制約
- 記者印の全レース自動収集は未実装（上記）。現状の記者系ルールの母数は
  ウォッチ分＋解析キャッシュ3日分に限られる。
- PRO予想の構造化データは 2026-10-25 以降のみ（それ以前のメモは予想として
  読めない）。ルールの長期検証は今後の蓄積待ち。
- KEIRINCRAFT のレースID は DB 側が null のため、（レース日・会場・レース番号）
  で突合している。同日同会場の開催が複数ある場合は混ざる可能性がある。
- 精算は払戻金JSON 基準。JSON が無い結果行は的中なしとして扱う。
- 本番 repo（keirin_cloud）には一切触れていない。DB は読み取りのみ。
